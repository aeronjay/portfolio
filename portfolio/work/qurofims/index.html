QUROFIMS

Walkthrough: filing a lost report, getting a QR flyer, admin approval and the student's notification

1 / 10

The Project

On a university campus, things go missing every day: umbrellas, ID laces, tumblers, calculators, chargers. Lost and found usually runs on a logbook at an office, notices on a bulletin board and posts in student group chats. Owners and finders rarely end up looking in the same place at the same time.

QUROFIMS is a QR code-based lost-and-found system that puts both sides in one place. Students report what they lost and get a printable QR flyer for it. Finders report what they found, or scan a flyer and reach the owner directly. A matching engine pairs lost and found reports, and the lost-and-found office confirms each match before contact details are exchanged.

I built it as a freelance project for a client at a university.

The client's name and data are kept private. The screenshots on this page come from a local demo build with generated data.

Key Features

QR flyers that open the item page

Every lost report gets a QR code that encodes the public URL of its item page, so anyone who scans a printed flyer with a regular phone camera lands on the report without installing anything. From there, a finder taps "I Found This Item" and leaves a name and email. The owner gets an in-app notification and an email with the finder's contact details. Signed-in students can also scan from an in-browser camera scanner.

Automatic matching with confidence scores

When a report comes in, the server scores it against every open report of the opposite type. Category is worth 35 points, item name 10, description keyword overlap 25 (with stop words removed), location 15, and how close the dates are 15, falling to zero after 7 days. A pair that scores 40 or more becomes a match labeled High (75+), Medium (50+) or Low, and both students are told a possible match exists.

Admin-confirmed handovers

Matches start out pending. The office reviews the lost and found reports side by side and can approve, reject, or undo an approval. Approving sets both reports to Matched and emails each person the other's contact details. Undoing reverts both reports and sends a correction email. Admins can also link two reports by hand when the algorithm misses a pair. Approvals, undos and claims are written to an audit log.

Verified accounts and roles

Sign-up sends a 6-digit code by email that expires after 10 minutes. The code is kept in its own pending collection, apart from user accounts, and the form only creates the account after the code checks out. Students and admins sign in on separate pages. A Next.js proxy (the new name for middleware) keeps signed-out users and non-admins away from protected pages, and every admin API route checks the role again on the server. Admins can edit accounts, reset passwords, deactivate users, or delete them along with everything they own.

The Challenge

The Problem

A lost-and-found system has a trust problem built in. If found items are listed publicly, anyone can scroll through them, spot a nice calculator and say it's theirs. If nothing is shared, owners and finders never connect. And a matching algorithm that's sometimes wrong shouldn't be handing a stranger's phone number to someone on its own.

The Decision

I split what each role can see. The public list shows only lost items: what people are looking for. A found report is visible only to admins, the person who found it, and an owner whose lost report has been matched to it. To get an item back, you have to describe it yourself in a lost report instead of picking it from a list. The matcher only suggests: every automatic match waits in the admin queue, and the email that gives both people each other's full contact details goes out only after someone in the office approves it.

The Tradeoff

It adds a human step. Even a high-confidence match waits for an admin before the owner hears from the finder, so how fast an item comes back depends on how often the office checks the queue. I accepted that because a wrong automatic release leaks a student's contact details and can send an item to the wrong person, which is worse than a delay. The QR flyer is the exception on purpose: a finder who scanned it is already looking at the owner's own report, so that path connects them directly.

The Result

Students can file and search reports from their phones, a printed flyer takes a finder straight to the right report, and the office works from a scored review queue instead of a logbook. Contact details are exchanged after a person has checked the match, and there's a record of who approved what.

Technical Details

It's one Next.js 16 App Router codebase: React pages and API route handlers side by side, with Prisma on MongoDB. Sign-in uses the NextAuth credentials provider with bcrypt-hashed passwords and 24-hour JWT sessions that carry the user's role. Styling is Tailwind CSS with DaisyUI.

The app runs on Render's free tier, which shaped two decisions. Next.js builds in standalone mode and the Node heap is capped at 384 MB to stay under the 512 MB memory limit. Render also blocks outbound SMTP, so email goes through the Gmail REST API over HTTPS: the server trades an OAuth refresh token for an access token and sends the message with plain fetch. When the Gmail credentials are missing, the email module logs the message instead of sending it, so local development never sends real email.

Matching starts after the new report is saved and doesn't hold up the response. Before creating a match it checks whether that lost and found pair is already linked, so the same pair never shows up twice in the queue. Photos, up to three per report and checked for type and a 5 MB limit in the browser, are stored as base64 data on the report itself, which kept the first version free of a separate storage service.

What I'd change today

The rule that contact details wait for an admin isn't enforced everywhere. The item endpoint strips the contact fields from the report, but it still returns the reporter's account record, including their email and student ID, to anyone who opens the page. The "I Found This Item" endpoint doesn't require a login and returns the owner's contact details to anyone who submits a name and an email. Skipping the admin on the flyer path is the right call, but it still needs a login and a rate limit. Registration has the same kind of gap: the server takes the browser's word that the email code was verified instead of checking it again. I'd build every response from one serializer that returns only what that viewer is allowed to see, and verify the code on the server when the account is created.

Matching runs in a promise that starts after the response is sent, and it loads every open report of the opposite type into memory. That works on a long-running server like Render's, but on a serverless host the work could be cut off, and it gets slower as reports pile up. I'd move it to a background job and narrow the candidates in the database query by category and date. I'd also move photos to object storage and keep only their URLs on the report, because right now the missing items list sends every photo inline.
