Event Desk

Freelance · Full Stack · React · Supabase · 2026

Walkthrough: searching, filtering, viewing and creating events

1 / 10

The Project

An events office receives a steady flow of requests from outside organizations: invitations, sponsorships, donations, medical missions and financial assistance. Every request has an event date the team has to act on before it passes.

They tracked all of it in one Excel sheet. As it grew to hundreds of rows, past events sat next to upcoming ones, and the only way to know what was coming up was to scroll and sort by hand. Events slipped by without anyone noticing until the date had already passed.

Event Desk replaces that spreadsheet. It separates active requests from finished ones, puts today's and upcoming events on the dashboard, and sends reminders to the team so nobody has to go looking. It's in daily use by the client.

The client's name and data are kept private. The screenshots on this page come from a demo build with generated data.

Key Features

Automatic daily email reminders

A scheduled job runs every day and emails each user about their upcoming events 5 days before, 1 day before and on the day itself. The email groups events into Today, Tomorrow and Upcoming, skips anything already done or discontinued, and works out dates in Manila time so a reminder never lands a day early or late. Users opt in or out from their settings.

Telegram notifications

One click on "Send to Telegram" posts a formatted summary of the event to the team's group chat, with its attachments sent as photos with captions. The team already lived in Telegram, so the information reaches them there instead of waiting for them to open the app.

Filtering and a clear past vs. upcoming split

Finished requests move to a separate History view automatically. The active list can be searched and filtered by type, status, event date, date received and date created, and sorted on the server, so it stays fast no matter how many records pile up.

Automated daily backups

A GitHub Actions job dumps the Postgres database every night, compresses it, uploads it to Cloudflare R2 and deletes copies older than 7 days. The office's records went from one Excel file on one machine to a hosted database with a week of restorable backups.

My Contribution

This was a solo freelance build. I gathered requirements with the client, designed the schema, and built, deployed and maintain the whole system:

  • The React + TypeScript frontend: dashboard, filterable and paginated request table, history view, detail panel and create/edit forms.
  • The reminder pipeline: a Supabase edge function, a Postgres function that picks which users to notify, and HTML emails sent over SMTP.
  • The Telegram integration, including sending attachments as captioned media.
  • An admin panel where superadmins change each form field's label, input type, dropdown options, default value, required flag and color coding without a code change.
  • Direct-to-storage file uploads using presigned Cloudflare R2 URLs.
  • Role-based access (user vs. superadmin), an Excel export, and the nightly backup job.

The Challenge

The Problem

The spreadsheet didn't fail all at once. It got slower to use with every row. Past and upcoming events were mixed together, and seeing what needed attention depended on someone remembering to sort and check. A better spreadsheet wouldn't fix that, because the real problem was that someone had to remember to look.

The Decision

I built the app around two ideas. First, the list should only show what's still open: a request's status decides whether it's active or history, and the dashboard pulls out today's and upcoming events on its own. Second, the system should come to the team. Daily emails and Telegram messages bring upcoming events to people instead of waiting for them to open a page.

The Tradeoff

Moving off Excel meant giving up its total flexibility, so I made the form itself configurable. Admins can change labels, dropdown options and required fields from the app. Adding a brand-new field still needs a database column, because I kept the data in typed, queryable columns instead of a free-form JSON blob. That's what keeps filtering, sorting and the Excel export reliable.

The Result

The team works from one shared record per request instead of one growing spreadsheet. Past events are out of the way, upcoming ones arrive in their inbox and chat, and most change requests are handled by the client's own admins without me.

Technical Details

A React 19 + Vite single-page app talks to Supabase directly. Postgres row-level security policies enforce access, and Supabase Auth plus a profiles table supply the user's role. There's no separate API server. Anything that needs a secret runs in Deno edge functions: presigning R2 uploads, calling the Telegram Bot API, and sending reminder emails over SMTP.

Bandwidth on the hosted database was a real constraint, so the table is paginated, filtered and sorted on the server. The dashboard tiles use count-only queries, and the event lists select only the columns they display. Loading every row happens only for an explicit Excel export.

Attachments go from the browser straight to R2 through presigned PUT URLs, so file bytes never pass through Supabase. Only the file name, URL and key are stored on the request.

What I'd change today

I'd keep the RLS policies and database functions in versioned migrations in the repo instead of only in the hosted database. That's the part of the system that's hardest to review and reproduce right now.

I'd also put the "active vs. history" status rule in one place, a Postgres view or generated column, instead of repeating it in the frontend queries, the dashboard and the reminder job. That would remove a whole class of drift bugs when statuses change.
